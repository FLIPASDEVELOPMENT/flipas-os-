# OWNER Console

The existing authenticated app adds `/owner`, `/owner/policies`, `/owner/approvals`, `/owner/team` and `/owner/profitability`. Each server page, the nested layout and each mutation independently require an active OWNER. `/api/owner/summary` returns 401 for anonymous and 403 for other roles, with private/no-store responses. ADMIN does not receive OWNER reports; existing authorized Phase 2 estimator approvals remain available. No new authentication system or accounts are created.

The additive migration `202610070004_owner_console` creates FinancialPolicy immutable versions, a singleton active-policy pointer and `Estimate.financialPolicySnapshot`. Initial values explicitly requested by the owner are monthly projected revenue $30,000, monthly fixed overhead $2,000, target gross margin 35%, minimum gross margin 20%. A conservative initial discount threshold of 0 requires review for every nonzero discount; OWNER can change it. Initialization is audited; subsequent saves require a reason, check the prior version, update the pointer and audit before/after in one serializable transaction. Database triggers disallow rewriting/deleting policy versions. Existing estimates receive an empty legacy snapshot and retain the legacy workflow.

Allocation is proportional to tax-exclusive, post-discount revenue: contract value × monthly fixed overhead ÷ projected monthly revenue. The initial ratio is 6.666666…%. Decimal calculations retain full precision and round only the allocation to cents, half-up. Automatic allocation replaces per-line overhead in the total to avoid double counting. Per-line overhead remains available in historical line snapshots; it is not additionally added to the policy-backed project allocation. Projected revenue must be positive, fixed overhead nonnegative, minimum margin no greater than target and target below 100%.

New estimates from scratch inherit the active policy; existing drafts, duplicates and revisions retain their captured historical policy. Catalog direct-cost snapshots remain unchanged. The policy supplies target margin and minimum floor; a stricter catalog/item minimum is retained, with target at least that floor. Manual price overrides remain proposals requiring explicit review. Policy updates never rewrite old estimate versions. The builder displays live policy-based totals; server calculations are authoritative. Sales receives only margin/discount rules and the derived overhead ratio, never the confidential monthly plan amounts. Customer HTML/PDF projections exclude all policy/internal costs.

Executive metrics use live database counts and contract/pipeline records. Accepted contracts in the current America/New_York calendar month are explicitly bookings, not cash receipts or recognized revenue. The $30,000 plan is labeled a projection. Project profitability uses accepted contract value and snapshotted direct cost/overhead; recorded actual costs are non-final. No final actual profit is invented. Team overview selects only name, email, role and active status; no password hashes or session data are exposed. Team management remains the existing secure administrator provisioning workflow.

Local update: stop Next; preserve `.env` and PostgreSQL volume; fetch the existing Phase 2 branch; run `npm ci`, `npm run db:generate`, `npm run db:migrate`, `npm run dev`. Log in with the existing OWNER and open Owner console. No new secrets or environment variables are required.

Validation: 17 unit tests including OWNER/role denial, decimal allocation and policy validation/projection; existing CRM and estimator integration; dedicated OWNER integration for permissions, stale versions, database immutability, audit, snapshot preservation and active-policy inheritance. OWNER HTTP checks on standalone Node and Docker exercise all five pages/API for OWNER, SALES, ADMIN and CREW plus anonymous requests. Disposable databases must end `_test`. `npm run test:owner` and `npm run test:owner:http` use that explicit database URL. Lint, TypeScript and production build are required. No merge or production deployment is part of this change.

Verified production build, Docker runtime build and Chromium desktop/mobile policy-save interaction. Existing Phase 1 CRM and Phase 2 estimator integration scenarios pass. Browser fixtures/screenshots and credentials remain outside Git.
