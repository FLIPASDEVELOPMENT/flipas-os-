# Team & Permissions — Phase 4

Branch: `feature/phase-4-project-operations`. OWNER administers employees at `/owner/team`, using existing database sessions, salted scrypt password hashes, roles and project membership. No separate authentication system, invitation email or external communication is introduced.

## Account procedure

1. Sign in as OWNER and open **Owner console → Team & permissions**.
2. Expand **Create employee account**. Enter name, unique email and employee role: ADMIN, SALES, PROJECT_MANAGER or CREW. OWNER/CUSTOMER creation and promotion to OWNER are unavailable here.
3. Supply a unique initial password of 12–256 characters, preferably generated by a password manager. Confirm it and share privately using a secure channel; do not use chat, source code or command-line arguments. The interface never retrieves or redisplays passwords.
4. The employee signs in with that initial password. Before any workspace access, `/account/password` requires the current password and a different personal password. The change revokes all sessions and signs the employee out. Sign in again with the personal password.
5. For PROJECT_MANAGER/CREW, expand **Authorized projects** and select the precise project identifier. Membership grants operational access; assign individual tasks separately in Project Workspace. Only open projects accept new grants; existing access can also be revoked from closed projects.

Existing accounts do not require a password change after migration. OWNER can reset an account to a new initial password, but cannot view its old password. Reset revokes all sessions and requires another personal password change. All users can change their own password through the workspace navigation.

## Server-enforced permissions

| Role | Access |
| --- | --- |
| OWNER | Team administration, all projects, financial policies, restricted project finances and approvals |
| ADMIN | Existing commercial permissions and project operations; no OWNER administration or restricted project finance |
| SALES | Existing assigned commercial records and related projects read-only; no team administration or OWNER reports |
| PROJECT_MANAGER | Managed/explicitly assigned project operations; no restricted financial payloads |
| CREW | Explicitly assigned projects, assigned tasks and own operational records; no restricted financial payloads |
| CUSTOMER | No operational workspace or administrative access |

Each administrative Server Action checks Origin and OWNER session. Transactional services recheck the actor's current active role and password-setup status. Form-submitted roles/IDs do not establish permission. Pending password setup blocks application routes and authenticated APIs; only the authenticated password-change flow is permitted. Project services retain assignment checks, financial DTO filtering and evidence authorization.

Deactivation and role changes revoke every session and clear project membership, manager assignments and task assignments. Reactivation never restores those grants implicitly. This preserves projects, financial snapshots, completed records and historical events; task unassignment increments its version. Project removals and account changes are audited without passwords, password hashes or session tokens. Revocation applies to subsequent server requests; already rendered browser content is not remotely erased.

The last active OWNER cannot be deactivated or demoted. A transaction advisory lock serializes administrative changes, including simultaneous attempts against different OWNER accounts. User row locks also protect login session issuance against concurrent password resets/deactivation. Additional OWNER provisioning remains an existing privileged bootstrap CLI operation, outside this interface; restrict shell/database access.

## Incremental migration and safe Mac update

New migration `202610100001_team_password_setup` adds only `User.passwordChangeRequired BOOLEAN NOT NULL DEFAULT false`. No earlier migration, password, role, account status, financial policy or existing record is changed. Do not use `prisma migrate reset` or delete the PostgreSQL volume.

Stop Next.js and the AI worker with **Control+C** in their respective terminals. Leave Docker/PostgreSQL running. In a new terminal:

```sh
cd ~/Projects/flipas-os-
git status --short
```

If this lists your changes, preserve them before updating; do not discard them. With a clean working tree, first make a private database backup:

```sh
umask 077
mkdir -p "$HOME/FLIPAS-backups"
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > "$HOME/FLIPAS-backups/before-team-$(date +%Y%m%d-%H%M%S).sql"
```

Check the command succeeded. The backup contains private application data; keep it out of Git and protect it. Then:

```sh
git switch feature/phase-4-project-operations
git pull --ff-only origin feature/phase-4-project-operations
npm ci
npm run db:generate
npm run db:migrate
npm run dev
```

Keep `.env` unchanged. Restart the existing AI worker in another terminal with `cd ~/Projects/flipas-os-` and `npm run worker:ai`. This update does not enable Zoho sending or change Emergency Pause, OAuth, AI limits or financial rules. Open `http://localhost:3000/owner/team` with OWNER. Test a new employee, mandatory password setup, project grant/removal and session revocation using your own test account.

## Repeatable automated checks

```sh
npm run lint
npm run typecheck
npm test
npm run build
npm run test:team:local
```

`test:team:local` creates a separate randomly named `*_test` database through the existing Docker PostgreSQL service, applies migrations, runs team integration tests and removes that test database. It never resets your application database. Direct `test:team` and `test:team:http` require a disposable `*_test` database; HTTP tests also require a separately running production server and `SMOKE_BASE_URL`. Do not direct them to the application database.

Coverage includes all roles, OWNER escalation denial, concurrent last-OWNER protection, duplicate emails, password hashing/setup/reset, session revocation, assignment removal, closed-project revocation, financial filtering, forged Server Actions, cross-Origin denial and HTML/RSC/API authorization. RSC may encode a not-found denial in a streamed HTTP 200 response; tests require the denial digest and absence of administrative content, not only a status code.

Account invitations, MFA/SSO, password expiry and user-directory pagination remain future work. Initial passwords must be transferred securely by OWNER; there is no automatic delivery or public password-reset endpoint.
